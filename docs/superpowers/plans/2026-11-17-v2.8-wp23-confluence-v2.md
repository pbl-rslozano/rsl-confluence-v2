# v2.8 WP23 — Confluence v2 (challenger beside Classic) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add **Confluence v2**, a second scoring engine that runs in the same scan as Classic.
- It is recorded on each Classic ledger row as a compact `v2` field that carries v2's own config id.
- It is compared with Classic head-to-head, on the same rows and the same outcomes, in a collapsed ledger section.
- It is shown only as an optional "Confluence v2 (test)" line in the detail sheet (a setting, default off).
- Classic scoring, the list, the labels and the Classic config id `5c30b5c39f5ba3f2` do not change.
- Nothing switches over without a later owner decision.

**Architecture:**
- **Pure core.** Two new modules without I/O:
  - `lib/confluence-v2-inputs.ts` turns the 18 voters into volatility-standardised, clipped per-bar inputs (the ADR-0017 table);
  - `lib/confluence-v2.ts` aggregates them per bar, applies the calibrated gain and the hysteresis (enter |score| ≥ 55, back to NEUTRAL below 40), and produces `V2Result`, the compact ledger field `V2Compact`, and the v2 config id.
- **No stored hysteresis state.** A row's v2 label is a pure function of its own 1,000-bar window: the hysteresis runs over the last `V2_HYST_BARS` (300) per-bar v2 scores of that window, starting NEUTRAL. Live rows, catch-up rows, the worker, the main-thread fallback, the recorder and replay therefore give the same label for the same bars.
- **Recording (controller ruling, 17 Nov 2026).** v2 rides on the Classic row as `v2: { cfg, s, m, st }`, about 55 B per row (measured in Task 5). There are no extra rows.
  - `scan-jobs.ts` scores v2 beside Classic, for live jobs and for every catch-up window.
  - `scan-record.ts` `liveRow` and `scan-jobs.ts` `runCatchUp` attach the field.
  - The recorder and replay get it through the same functions.
  - The row's outcome is measured once and shared by both engines.
- **Comparison.** `lib/head-to-head.ts` builds a v2 view of each row that carries `v2`: the same row with v2's score, direction and strength. It retargets the shared Classic outcomes to v2's direction, so both engines are measured on identical bars and costs. The ledger dialog shows this in a collapsed section placed just before the Scenario check.
- **Classic untouched.** `indicators.ts`, `scan-pipeline.ts`, `engine-config.ts` and `engine-window.ts` are not edited. v2 imports from them read-only. `toLedgerRow` is unchanged; `v2` is assigned after it.

**Tech Stack:** Next.js 15 / React 19 static export, TypeScript run by `node --experimental-strip-types` (`scripts/run-engine-tests.mjs`), Web Worker scan (`scan.worker.ts`), Node 22 recorder, Playwright acceptance (`tools/e2e/acceptance.cjs`).

## Review Focus

1. **Hysteresis state must come out the same on every path, with nothing stored.**
   - Cases: a live row, then the same bar as a catch-up row after a restart; the worker versus the main-thread fallback; the recorder in Node versus the app in a WebView; replay with `--step 5`; a series that was closed for a week; two tabs.
   - Expected: identical `v2` for the same bars. State is never read from storage. A hole in the history (`contiguousTail`) shortens the window, so the hysteresis restarts NEUTRAL from the window's first bar on every path alike.
   - Consecutive rows agree: row t's label equals the in-window state at t computed inside row t+1's window, on ≥ 99 % of fixture bars (the rate goes in the evidence).
   - Test owners: Tasks 3, 6, 7 and 10.
2. **Odd inputs to the hysteresis and the inputs.**
   - Cases: a score exactly 55 / −55 / 40 / −40; +60 → −60 in one bar; a suppressed bar in the middle of a held label; fewer than 300 scored bars (cold window); zero volume; FX (no low-volatility cap); a stock with the session filter or a split in the window; a flat series (σ = 0, ATR = 0); the 4h boundary and 1M bars.
   - Expected: no NaN and no throw. A zero divisor makes that input invalid, not ±1. A suppressed bar resets the state to NEUTRAL and records `s: null`. A sign flip by ≥ 55 switches directly. The window rules match Classic's.
   - Test owners: Tasks 2 and 3.
3. **v2 must not leak into anything Classic owns.**
   - Expected:
     - List cells, sort and counts are unchanged with the setting on or off.
     - MiniStat Confluence and the MasterBadge stay Classic.
     - Paper proposals and alerts read only `sc`/`m`/`st`.
     - The Classic report, the gate and the pre-registration give the same numbers on rows with and without `v2`.
     - Every Classic field of a row is unchanged by attaching `v2`.
     - The config id pin `5c30b5c39f5ba3f2` passes.
   - Test owners: Tasks 6, 8 and 9 (CV-2, CV-3).
4. **Untrusted and partial `v2` values in imports and backups.**
   - Cases: an earlier v2.8 CSV without the v2 columns; three of the four v2 cells filled; `s: 101`; `s: 12.5`; `m: 2`; `st: 3`; `cfg` that is not 16 hex; `s: null` with `m: 1`; `m: 0` with `st: 2`; extra keys; JSON, JSONL (recorder) and an encrypted WP28 backup.
   - Expected:
     - Old files import with `v2` null.
     - Every hostile or inconsistent value rejects the whole row; unknown keys are dropped.
     - Rows with `v2` round-trip through CSV, JSON and backup unchanged.
     - Rows without `v2` stay valid, and the comparison counts them as "not compared".
   - Test owners: Tasks 5 and 9.
5. **Running v2 in the same scan must stay cheap in time and in bytes.**
   - Cases: 100 series × a 1,000-bar window; catch-up of 48 rows × 100 series in the worker; a phone; a full 400,000-row ledger and a 20 MB backup.
   - Expected:
     - `scoreV2` averages ≤ 5 ms per 1,000-bar window and ≤ 2 × `scoreSeries` in the same run.
     - Catch-up stays in the worker (`allowMainThread: false`, unchanged).
     - `v2` adds ≤ 64 B per stored row (JSON), and the measured value is documented.
   - Test owners: Tasks 5 and 6.

## Spec conflicts and how this plan resolves them

| Spec text | Conflict | Resolution |
|---|---|---|
| "hysteresis (enter \|score\| ≥ 55, return to NEUTRAL below 40)" and "bands re-calibrated on noise to the same targets as Classic" | With both thresholds pinned, there is no band left to calibrate. | 55 and 40 stay exactly as written, as score thresholds. The calibration sets one gain `V2_GAIN`, with score = round(100 · clamp(V2_GAIN · bloc mean, ±1)). This is the same as moving both bands together on the bloc-mean scale. It also sets the STRONG band `V2_STRONG_BAND`. Rule: the **largest** grid gain whose worst noise cell is ≤ 6.0 % labelled, then the smallest STRONG band whose worst cell is ≤ 1.5 % STRONG. If no grid gain qualifies, stop and report. Never change 55/40 (Task 4). |
| Hysteresis needs state across scans, while every recorded score must be reproducible from the bars alone ("live == replay", fixed window) | A stored per-series state would differ between the app, the recorder, catch-up and replay, and would survive gaps. | No stored state. The label is the hysteresis over the last 300 per-bar v2 scores **inside the row's own 1,000-bar window**, starting NEUTRAL. The state is forced on every bar with \|score\| ≥ 55 or \|score\| < 40, so 300 bars almost always contain the decisive bar. Continuity is measured (Review Focus 1). |
| "recorded under its own config id" | A separate row per engine would double the ledger, halving its retention and the bars that fit in a 20 MB backup. | Controller ruling: v2 is a compact field on the Classic row. Its `cfg` member carries v2's config id. One outcome per row is shared by both engines. |
| §3 item 4 lists "Collapsed new sections at the end of the ledger dialog (Scenario check)"; WP23 needs a head-to-head view | The head-to-head section is not named in the parenthesis. | It is the same allowed kind (collapsed, at the end of the ledger dialog), placed directly **before** the Scenario check so that SC-7's "last element" assertion is unchanged. It is added to `DS2_ALLOWED.ledger`, and ADR-0017 records the placement. The spec text is not edited beyond the §4 Status bullet. |
| "scored in the same scan and recorded under its own config id" | A custom scoring profile changes Classic's config id; the spec does not say whether v2 follows it. | v2 is a fixed challenger and ignores scoring profiles. It has one config id. The head-to-head compares it with whichever Classic config the ledger dialog shows, on the rows of that config. |
| "band position" (spec example of a measure) for Bollinger/Keltner | Band position is already scaled by the band's own width, so dividing it again by ATR or σ would double-scale it. | Bollinger: (close − SMA20) ÷ (2·σ20). Keltner: (close − EMA20) ÷ (2·ATR10). Both are the measure divided by its own band half-width. Recorded in the table. |
