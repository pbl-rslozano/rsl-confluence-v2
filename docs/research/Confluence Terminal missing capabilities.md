# Measure the edge before automating anything

v1.0 2026 · 31 October 2026 · Personal project · Subject: rsL Confluence Terminal v2.1 2026 (build 20261031)

*Reading convention: **[code]** marks a fact verified in the v2.1 source tree at `/home/claude/rsl-confluence` (linked to the file). A link marks published evidence. **[unverified]** marks something these notes could not confirm from a primary source. Untagged reasoning, effort estimates and gate thresholds are my own inference and design proposals. Nothing here is legal, tax or financial advice.*

The single most important missing capability in Confluence Terminal v2.1 is measurement, not data or indicators. The app does not persist a single signal. It has no backtest, ledger, forward test, paper broker or cost model, so it cannot report a hit rate or a net expectancy for its own Master Signal **[code]**. The 2.02 engine changes were also made in place, without a configuration hash, so no recorded baseline exists to compare against **[code]**. Every other gap is downstream of that one. Against mature tools, v2.1 covers only the technical-screener layer, and it is missing what that layer now treats as table stakes: multi-timeframe confluence, user-defined screening rules, alerts that leave the app, a signal hit-rate report, and (for a scanner that already offers a Bybit perpetual source) funding, open-interest and liquidation context. For assisted and automated trading, everything is missing end to end: positions, sizing, stops, a journal, a risk gate, notifications and any Claude integration. The good news is that the highest-value fixes are cheap. Most need no new network host under ADR-0003. The data enrichments with the best evidence are computed from candles the app already downloads. And Claude can start as a ledger analyst that reads an exported file, which needs no change to the app's network posture at all. The recommended order is therefore: harden and freeze (about a week), then measure (2–3 weeks to build, then a 3–6-month forward clock), with data enrichment and alerts running in parallel as logged-but-unscored fields. Assisted execution on exchange demo accounts comes only after a pre-registered edge test passes. Automation without a human in the loop comes last, and only for rule-based signals with the LLM outside the order path.

## v2.1 records nothing, so no signal can yet be scored

### What the code actually lacks

The engine is careful about what it computes and silent about what happens afterwards. Scan rows live only in React state. The IndexedDB store holds candles, and the StoragePort collections are `meta`, `identity`, `preferences`, `audit` and `audit_meta`. The hash-chained audit trail logs app, preference, identity, backup and clock events, but never signals ([page.tsx](/home/claude/rsl-confluence/apps/confluence/web/src/app/page.tsx); [history-store.ts](/home/claude/rsl-confluence/apps/confluence/web/src/lib/history-store.ts); [ADR-0002](/home/claude/rsl-confluence/docs/adr/0002-data-model.md)) **[code]**. A grep across the app, gateway, adapters and Tauri source finds no implementation of backtest, walk-forward, ledger, paper trading, journal, PnL, slippage, commission or fee. The word "ledger" appears only in two comments, and both make the ledger a precondition for future work: one says a "redesign should follow measurement of a recorded signal ledger" ([indicators.ts](/home/claude/rsl-confluence/apps/confluence/web/src/lib/indicators.ts)), and the gateway says it will expose no order endpoint "until the signal engine has demonstrated an edge net of costs against a recorded ledger" ([server.mjs](/home/claude/rsl-confluence/apps/confluence/gateway/server.mjs)) **[code]**. The app's own architecture already names the gate this report recommends. It just never built the thing that opens it.

The few outcome statistics that do exist cannot stand in for one. The analogue panel's hit rate is in-sample, gross of costs, and measured close-to-close from the signal bar, not from the next bar's open. The UI correctly labels it "Descriptive only — not a validated forecast" ([pattern-signal.ts](/home/claude/rsl-confluence/apps/confluence/web/src/lib/pattern-signal.ts)) **[code]**. The 55/70 bands were set by hand from a null-calibration script. That script runs Gaussian and Student-t random walks at a 1h interval and writes nothing back, yet the same global bands apply to every timeframe from 1m to 1M. On that null, about 5% of noise bars get a direction and about 1.3% are STRONG ([null-calibration.mjs](/home/claude/rsl-confluence/apps/confluence/web/src/lib/null-calibration.mjs); [indicators.ts](/home/claude/rsl-confluence/apps/confluence/web/src/lib/indicators.ts)) **[code]**. That calibration is a real improvement on Build 2.01. But it defines only the null. It does not define an outcome, so a BUY still cannot be shown to beat chance. The 37 engine assertions and 21 FVG assertions pin defect fixes and noise rates, not performance. No incremental-replay non-repaint test exists: the only related check is that a repeated call on identical input is deterministic. And no market-client test runs against recorded exchange payloads ([engine.test.mjs](/home/claude/rsl-confluence/apps/confluence/web/src/lib/engine.test.mjs)) **[code]**.

Two subtler defects would contaminate any ledger built on today's code. First, the engine sees a variable amount of history. A first scan has about 199 bars, and stored history later lengthens this to the `ENGINE_BARS = 1000` cap ([page.tsx:127,549](/home/claude/rsl-confluence/apps/confluence/web/src/app/page.tsx)) **[code]**. Recursive indicators such as EMA, ADX, PSAR, Supertrend and Ichimoku therefore give different values for the same asset and bar on different devices or sessions. Freqtrade's documentation names this *warm-up bias*: recursive indicators give "different last-bar values depending on how much history they were seeded with" ([Freqtrade recursive analysis](https://www.freqtrade.io/en/stable/recursive-analysis)). Second, the reversal engine still carries two defects that 2.02 fixed only in `indicators.ts`. Its local RSI returns 100 on a flat series, and its Supertrend is seeded bullish by default ([reversal.ts](/home/claude/rsl-confluence/apps/confluence/web/src/lib/reversal.ts)) **[code]**. Both feed the alerts and the analogue features.

### What the measurement layer must contain

The cleanest design keeps the TypeScript engine as its own backtest kernel. A Node script replays archived closed klines through the same pure functions the browser uses. Re-implementing 18 indicators in Python for Freqtrade or vectorbt would create a parity risk: the Python backtest would no longer be testing the shipped engine. Freqtrade (GPLv3, release 2026.10 on 30 October 2026) is still worth copying for its two bias detectors ([PyPI freqtrade](https://pypi.org/pypi/freqtrade/json)). The first is `lookahead-analysis`, which re-runs a backtest for each signal with the data sliced at that signal and flags any indicator that changes. The second is `recursive-analysis`, which recomputes indicators at startup lengths of 199, 499, 999 and 1,999 bars and reports the variance of the last value ([Freqtrade lookahead analysis](https://www.freqtrade.io/en/stable/lookahead-analysis/); [Freqtrade recursive analysis](https://www.freqtrade.io/en/stable/recursive-analysis)). Both are about a day's work each as TypeScript tests. Freqtrade's single-pair verification also false-flags any logic that ranks pairs against each other, so a top-N ranker needs its own universe-level slice test ([Freqtrade lookahead analysis](https://www.freqtrade.io/en/stable/lookahead-analysis/)).

History should come from data.binance.vision. It publishes free daily and monthly ZIPs of spot, USD-M and COIN-M klines and aggTrades, each with a SHA-256 `.CHECKSUM` file. Spot timestamps switch to **microseconds from 1 January 2025**, and archives "may be updated at a later date" ([binance-public-data README](https://github.com/binance/binance-public-data/)). The downloader is a side tool, not the app, so it does not touch the app's CSP. The universe must be point-in-time: "rank only markets that existed then", keep delisted symbols until their final trading date, and log the daily universe ([CoinAPI, 13 Mar 2026](https://www.coinapi.io/blog/how-to-eliminate-survivorship-bias-in-crypto-backtesting)). Today's universe is ranked only by current 24h quote volume, with no liquidity floor and no point-in-time filter ([market-client.ts](/home/claude/rsl-confluence/apps/confluence/web/src/lib/market-client.ts)) **[code]**, so backfilling today's top 100 imports survivorship bias. Crypto survivorship bias has been measured at **62% a year for equal-weighted portfolios** ([Ammann et al. 2022](https://diffform.netlify.app/publication/2022_liebi_survivorship)). One key unknown remains: whether data.binance.vision keeps archives for delisted pairs such as LUNAUSDT **[unverified]**. Check that by browsing the archive before trusting the free universe.

Each ledger row is one symbol × timeframe × closed bar, and it needs four groups of fields. *Provenance*: engine build, config hash, data source, archive checksum, warm-up length, point-in-time universe rank. *Signal*: raw score, label, onset flag, bars-in-state, the four bloc scores, the 18 sub-votes, the FVG multiplier and a regime tag. *Market*: close, next open, ATR, estimated spread, and funding for perps. *Outcomes*, filled in later at several horizons: return from the next open, return in excess of BTC and of the cross-sectional mean, MFE, MAE, and net return after costs. The report built on it should always show hit rate against the base rate with a Wilson interval, net expectancy with a block-bootstrap interval, a score-decile calibration table with a Brier score, and rank IC. Every backtest run should append its config hash, date range and results to a `trials.jsonl` file. The Deflated Sharpe Ratio ([SSRN 2460551](https://papers.ssrn.com/abstract=2460551)) and the probability of backtest overfitting via CSCV ([PBO paper](https://escholarship.org/content/qt4w1110bb/qt4w1110bb.pdf)) then take their trial count from that file, not from memory. Alongside the score, record five benchmarks: buy-and-hold, volatility-scaled buy-and-hold, a persistence-matched shuffled signal, the best single indicator, and a random walk. If the 18-vote confluence cannot beat a single 20-bar momentum sign, the other 17 votes add only complexity.

Power sets the timetable. Treating correlated coins as roughly 1.4–2 effective assets, 30 days of 4h bars yields only about **70–90 independent observations**, against about 783 needed to detect a 55% versus 50% hit rate at 80% power. So the forward clock must run 6–12 months at 1h/4h, not 30 days. A pre-registered primary test makes six months usable. Take the per-bar cross-sectional Spearman rank IC between the raw score and the 6-bar forward return in excess of BTC, on 4h bars, for a point-in-time top-30 universe sampled every sixth bar. That yields about 270 cross-sections, enough to detect an IC near 0.03 if excess returns are close to independent across coins. Overlapping horizons need HAC or block-bootstrap errors, because serial correlation can overstate an annualised Sharpe by **up to 65%** ([Lo 2002](https://ideas.repec.org/a/taf/ufajxx/v58y2002i4p36-52.html)). The total build is roughly 2–3 weeks part-time: downloader and store, replay backtester, outcome filler and report, purged walk-forward with DSR and PBO, and a simulated broker.

### Costs decide whether any edge survives

v2.1 has no cost model, and every published edge in this space is small enough for costs to erase it. At base tiers, perpetual taker fees are **0.05% on Binance, 0.055% on Bybit and 0.06% on Bitget**, with makers at 0.02% on all three ([Binance FAQ](https://www.binance.com/support/faq/360033544231); [Bitsgap, 9 Sep 2026](https://bitsgap.com/blog/bybit-trading-fees-explained-what-it-costs); [Bitget support](https://www.bitget.com/support/articles/12560603892733)). Bitget spot is 0.10%, or 0.08% with BGB ([Bitget support](https://www.bitget.com/support/articles/12560603892733)). Binance spot is about 0.10% per a third-party source, not re-verified against Binance's own schedule ([TradersUnion](https://tradersunion.com/brokers/crypto/view/binance/fees/)). Perp funding has a built-in **0.01% per 8h** interest component, and if the premium stays between −0.04% and +0.06% the rate is exactly 0.01% ([Binance funding FAQ](https://www.binance.com/en/support/faq/introduction-to-binance-futures-funding-rates-360033525031)). On BitMEX in Q3 2025, BTC funding printed exactly that baseline in 78.19% of periods, which annualises to about 10.95% simple ([Coincub, 29 Sep 2026](https://coincub.com/blog/perpetual-futures-funding-rates-78-of-a-quarter-at-0-01/)). A week-long long perp at baseline therefore pays about 21 bp in funding, more than the round-trip fee.

The weakest number is slippage. These notes found no reliable 2025–2026 source on spreads or slippage for top-100 altcoins at retail size. That gap can be closed for free without amending ADR-0003. Snapshot the order book on the already-allowed `data-api.binance.vision` host a few times a day for the universe, and compute walk-the-book cost at $1k, $10k and $100k. After about two weeks that gives first-party slippage curves. Report all results at 1×, 2× and 3× the cost assumption so sensitivity is visible.

## The best new inputs are free filters, and most need no new host

### Evidence argues for filters, not new votes

v2.1 uses only public OHLCV candles and 24h tickers for USDT pairs. It has no funding, OI, liquidation, long/short, basis, order-book, trade, CVD, on-chain, news, sentiment, dominance or macro input ([market-client.ts](/home/claude/rsl-confluence/apps/confluence/web/src/lib/market-client.ts)) **[code]**. Before adding any of these, look at what the evidence says. None of the new data families supports a new equal-weight vote. Funding is the obvious candidate and the clearest warning. On BTC, weekly funding changes explain **12.5% of same-week price change**, yet have **zero predictive R² for the following week** ([Presto Research, Aug 2024](https://prestolabs.io/research/can-funding-rate-predict-price-change)). Funding was also positive 92% of the time in a BitMEX study, so a fixed "positive funding is bearish" rule would fire almost constantly ([DL News](https://www.dlnews.com/external/bitmex-study-finds-cryptocurrency-funding-rates-positive-92-of-the-time-revealing-a-structural-market-bias)). Order-book imbalance does predict direction, at 0.71–0.73 accuracy, but only at **500 ms horizons** on one day of Bybit BTC data ([arXiv 2506.05764](https://arxiv.org/html/2506.05764v2)). That is irrelevant to a 4h-to-daily scanner. Stablecoin exchange inflows predict BTC and ETH returns at 1–6 hours ([arXiv 2411.06327](https://arxiv.org/abs/2411.06327)), but the labelled-wallet data behind them is paid. Glassnode and CryptoQuant expose no free API ([Spark, mid-2026](https://www.spark.money/tools/bitcoin-onchain-analytics-comparison)). Inputs with better support act on the regime or the event, not on a pair's direction. The Fear & Greed Index leads BTC and ETH returns by about a week to a month in two peer-reviewed studies, though with short samples and two-way feedback ([CJEF 2025](https://journal.fsv.cuni.cz/article/riding-the-waves-of-crypto-sentiment-examining-the-dynamics-between-returns-and-sentiment-in-the-cryptocurrency-market/); [RBF 2024](https://ideas.repec.org/a/eme/rbfpps/rbf-08-2023-0224.html)). A market-maker study of more than 16,000 unlocks found about **90% create negative pressure**, starting about 30 days before the event and accelerating in the final week ([Keyrock](https://keyrock.com/from-locked-to-liquidity-what-16000-token-unlocks-teach-us/)). Macro releases barely move BTC: it was "orthogonal to all macro news… except CPI" through 2022 ([NY Fed SR1052](https://www.newyorkfed.org/medialibrary/media/research/staff_reports/sr1052.pdf)).

The resulting priority list favours inputs that cost nothing and change no ADR.

The derivatives series need one urgent decision even though they rank in the middle. Binance's `/futures/data/openInterestHist` and `/futures/data/basis` keep **only the latest month**, with a limit of 1,000 requests per 5 minutes ([Binance docs](https://developers.binance.com/docs/zh-CN/derivatives/usds-margined-futures/market-data/rest-api/Long-Short-Ratio)). The taker long/short ratio has the same 30-day cap ([binance_futures hexdocs](https://binance-futures.hexdocs.pm/BinanceFutures.USDM.MarketData-function-taker_long_short_ratio.html)). Funding history can be paged with no stated cap ([Binance docs](https://developers.binance.com/docs/zh-CN/derivatives/usds-margined-futures/market-data/rest-api/Long-Short-Ratio)). So positioning data cannot be backtested from the API alone. Every month not recorded is lost for good. Public liquidations come only over WebSocket, and `!forceOrder@arr` sends at most one snapshot per symbol per second, which under-counts cascades ([Binance WS docs](https://developers.binance.com/docs/derivatives/usds-margined-futures/websocket-market-streams/All-Market-Liquidation-Order-Streams)). The practical answer is to start a recorder for Bybit funding and open interest in Phase 1. Bybit's V5 public endpoints for funding history, open interest and account ratio sit on the already-allowed host ([ccxt Bybit implicit API](https://docs.ccxt.com/docs/exchanges/bybit/implicit-api)), although their own history depth and rate limits are **[unverified]**. Store the series as logged-but-unscored ledger fields. Binance futures data waits for an ADR amendment.

### The rule that keeps enrichment honest

Every new input enters as a logged field that does not affect the score. It is promoted to a filter only when the ledger shows that it separates outcomes, and each promotion attempt is logged as a trial so that it counts against the Deflated Sharpe hurdle. Without this rule, enrichment turns into a multiple-testing machine. Ten new inputs times a few thresholds times 13 timeframes will produce an apparent edge by chance alone. Every ADR-0003 amendment should name the host, its purpose, whether it needs a key (only CoinGecko's free Demo key does), and an R8 allowlist update, mirroring the existing table ([ADR-0003](/home/claude/rsl-confluence/docs/adr/0003-network-allowlist.md)). CoinGecko's free Demo plan allows 100 calls a minute and 10,000 a month ([CoinGecko](https://www.coingecko.com/learn/best-free-crypto-api)). One `/global` and one `/categories` call every 15 minutes uses roughly 6,000 a month, comfortably inside that.

## Alerts, Claude and execution all need a headless worker and a risk gate

### In-app reversal pop-ups are the only alert today

Alerts fire only for reversals that oppose the current trend at HIGH or MODERATE confidence. They are deduplicated with a 6-bar cooldown, capped at 12, and held in a `useRef` map and `useState`, so a reload loses them. No Notification API, sound, Telegram, email or webhook code exists. The Capacitor and Tauri plugin lists include no notification plugin. There are no alerts on Master Signal changes, score thresholds or price levels ([page.tsx](/home/claude/rsl-confluence/apps/confluence/web/src/app/page.tsx); [Cargo.toml](/home/claude/rsl-confluence/apps/confluence/desktop/src-tauri/Cargo.toml)) **[code]**. The deeper limitation is architectural. Scans run on a `setInterval` inside the page, and the service worker has no push or periodic-sync handler ([sw.js](/home/claude/rsl-confluence/apps/confluence/web/public/sw.js)) **[code]**, so nothing fires when the app is closed. Web Push would not fix this by itself. iOS supports it only for Home Screen web apps with a standalone manifest, with permission requested from a user gesture and Apple push endpoints allowed ([WebKit](https://webkit.org/?p=13878)). A server must still send each push, and v2.1 has no backend.

The same structural answer covers alerts, the ledger and eventual execution. Build one headless Node worker that imports the existing TypeScript engine, scans on a schedule, appends ledger rows, and sends notifications. Run it alongside the localhost gateway or inside it. This solves four problems at once. The ledger no longer depends on a browser tab staying open. Alerts work in the background. The engine stays a single code path for live scanning, replay and paper trading. And outbound hosts such as `api.telegram.org` stay out of the browser CSP. ADR-0003 governs the browser's `connect-src`, and R8 checks only the CSP ([release-check.mjs](/home/claude/rsl-confluence/tools/release-check.mjs)) **[code]**. A Node process could therefore reach new hosts without tripping R8. That would be a loophole in the spirit of the "no network at runtime" rule. ADR-0003 should be amended to list the worker's and gateway's egress hosts explicitly, and R8 extended to check a declared egress manifest. A Telegram bot is the simplest reliable channel for one owner. Its inline buttons also become the approve-or-reject surface later. The Telegram Bot API specifics (rate limits, callback handling) were not verified in these notes **[unverified]**. An outgoing JSON webhook would let the scanner plug into existing bot ecosystems without writing order code. Be cautious there: 3Commas confirmed an API-data disclosure incident and advised users to reissue keys and disable withdrawal permission ([DayTrading.com](https://www.daytrading.com/3commas)).

### Claude fits as analyst first, proposer second, never the order path

Public evidence does not support letting an LLM trade leveraged crypto on its own. In Alpha Arena Season 1 (crypto perpetuals on Hyperliquid, 18 October–3 November 2025, $10,000 per model), Qwen 3 Max won with +22% and GPT-5 ended at about −63%. The organiser attributed weak results partly to LLMs' poor handling of numeric time series ([GNcrypto](https://www.gncrypto.news/news/qwen-wins-alpha-arena-season-1-with-22-percent-returns/); [ForkLog](https://forklog.com/en/four-out-of-six-ai-models-suffer-losses-in-trading-tournament/)). In Season 1.5 on US equities, seven of eight models lost money, and Claude "finished in the red" ([Aihola](https://aihola.com/article/grok-wins-alpha-arena-trading)). These are two-week windows, reported through secondary sources and not cross-checked against nof1.ai, so they prove little about skill. They do show that an unconstrained LLM trader has no demonstrated edge. They also support the Terminal's existing split: compute features deterministically, and let the model reason over summaries, not raw candles.

Claude's highest-value job right now therefore needs no trading tools and no network change. Claude reads an exported ledger and a weekly journal. It writes performance summaries, flags decaying components, and proposes hypotheses, and each hypothesis is logged as a trial before it is tested. This needs exactly one policy change: amend ADR-0006 to allow a CSV or JSONL ledger export. Claude Code can then read the file, or a scheduled Claude Code task can review it weekly. The next step is a local, read-only MCP server over the ledger and the latest scan. It answers questions such as "which pairs are BUY-strong on 4h with a bullish 1d gate and falling funding?" The Anthropic MCP connector in the Messages API accepts only public HTTPS servers, not local STDIO ones. It supports per-tool allowlisting through `mcp_toolset`, and the docs recommend denylisting write tools where a human confirmation step is wanted. A `mcp-client-2026-09-15` beta adds tool-list pinning ([Claude Platform docs: MCP connector](https://platform.claude.com/docs/en/agents-and-tools/mcp-connector)). The Agent SDK, by contrast, supports local MCP servers ([Agent SDK MCP](https://platform.claude.com/docs/en/agent-sdk/mcp)). The local route keeps the gateway off the public internet. Do not adopt community CCXT MCP servers as a shortcut. One widely forked example can place orders, set leverage up to 100×, has no read-only or sandbox mode, and stores keys in plaintext JSON ([GitHub raz0r/ccxt-mcp](https://github.com/raz0r/ccxt-mcp)).

### Execution is missing end to end, by design

The app places no orders. It tracks no positions or portfolio, computes no PnL, and suggests no size, stop or target. Its only level-type output is a "Key Levels (20-bar)" panel. That panel mixes a previous-bar pivot with 20-bar extremes for R1, S1, R2 and S2, which is a non-standard construction ([page.tsx](/home/claude/rsl-confluence/apps/confluence/web/src/app/page.tsx)) **[code]**. The gateway is a credential checker and nothing more. It binds to 127.0.0.1, enforces Host and Origin allowlists, uses a per-session bearer token with constant-time comparison, and clears secrets on exit. It has no order, withdrawal, transfer or account-data route. The connected profile lives only in React state and is lost on reload ([server.mjs](/home/claude/rsl-confluence/apps/confluence/gateway/server.mjs); [exchange-auth.mjs](/home/claude/rsl-confluence/apps/confluence/gateway/exchange-auth.mjs)) **[code]**. One small bug: the README and dialog tell users to run `npm run gateway`, but no such script exists; the gateway's script is `start` **[code]**. That security core is the right foundation to extend.

What must sit between a signal and an order is a deterministic risk engine inside the gateway. It applies fixed-fractional or ATR-distance sizing rounded to exchange lot filters, a stop beyond the invalidating structure, caps on total open risk and on same-direction exposure per BTC-correlated cluster, daily and weekly loss locks, maximum leverage, a symbol allowlist, a kill switch that cancels everything, and a dead-man's switch on heartbeat loss. These are standard practitioner controls, and no source in these notes quantifies them. Every order, whether a person or Claude proposed it, must pass that code. Prompt instructions are not a control. The 2026 exchange precedent agrees. Binance's official MCP server acts inside a dedicated "Agentic sub-account", offers **no withdrawal scope**, and requires user confirmation before any order, cancel or transfer ([Binance Developers: MCP Server](https://developers.binance.com/en/docs/agent-native/mcp-server/agentic)).

Paper trading needs no new exchange code at first. A simulated broker over the ledger reuses the backtest's code path, so backtest, forward and paper results stay comparable. Exchange demo accounts then test the order code itself. Binance Demo Mode runs at `demo-api.binance.com` and matches live IP limits and filters "exactly". Binance also warns that its data is "not real market data", and that during maintenance orders cannot be placed or cancelled ([Binance Demo Mode](https://developers.binance.com/docs/binance-spot-api-docs/demo-mode/general-info), modified 30 Oct 2026). Bybit demo runs at `api-demo.bybit.com` under a separate UID. It supports orders, trading stops, positions and private streams, but keeps demo orders only 7 days ([Bybit Demo Trading](https://bybit-exchange.github.io/docs/v5/demo)). Bitget switches to demo with a `paptrading: 1` header and a demo key ([Bitget demo REST](https://www.bitget.com/docs/classic/demo-trading/rest-api)). That 7-day retention is one more reason the Terminal must own its journal from the first paper trade. The journal needs the signal ID, the indicator snapshot, planned and actual fills, fees and funding, MAE and MFE, the R-multiple, and a manual-versus-automatic flag. Idempotency comes from a client order ID derived from the signal ID. Reconciliation treats the exchange as the source of truth and halts new entries on any mismatch. For order placement, a thin native adapter per exchange (`placeBracket`, `cancel`, `flatten`) is safer than relying on CCXT's demo-mode handling. CCXT is actively maintained, at v4.5.91 as of 29 October 2026 ([npm ccxt](https://registry.npmjs.org/ccxt/latest)), but its per-exchange demo and TP/SL behaviour is **[unverified]**.

### Saudi access and regulation remain unverified

Two facts must be settled personally before any live order, and these notes could not settle either. On access, a June 2026 secondary list of Binance Futures restricted countries names the US, UK, Canada, Australia, the Netherlands and sanctioned regions, and does not mention Saudi Arabia ([CoinPerps, 3 Jun 2026](https://www.coinperps.com/learn/binance-futures-restricted-countries)). No primary Binance statement was found, and Bybit and Bitget were not checked **[unverified]**. On regulation, the official record found consists of a 2018 standing-committee statement that virtual currencies are "illegal and unlicensed", with no party licensed ([Baker McKenzie, 15 Aug 2018](https://blockchain.bakermckenzie.com/2018/08/15/unauthorized-cryptocurrency-declared-illegal-in-saudi-arabia/)), and a Ministry of Finance warning on 20 August 2019 ([Lightspark](https://www.lightspark.com/knowledge/is-crypto-legal-in-saudi-arabia)). No 2026 primary SAMA or CMA statement on retail access to offshore exchanges or derivatives was found **[unverified]**. This is factual context only, not legal advice. Confirm the current position with SAMA, CMA and Ministry of Finance publications, or with Saudi counsel, and read each exchange's restricted-country terms directly. The software should not assume perpetuals stay available. It should degrade to spot-only when access changes, treat an HTTP 451 as permanent for the session, and never help route around a geo-restriction.

The gateway's own comment already encodes the central gate: no order endpoint until an edge net of costs is shown on a recorded ledger **[code]**. The no-go branches matter as much as the go branches. If G1 fails because the confluence score cannot beat a single momentum sign, the right move is simplification, not more data. Collapse the nine-member trend bloc, re-sign or drop the contrarian oscillators on 4h-and-slower bars, and replace ±1 votes with volatility-scaled inputs plus hysteresis. Ship that as a new hashed configuration logged beside v2.1, and restart the clock. The trend bloc is a priority target because, under the current formula, one breakout indicator moves the score 4.5 times as much as one trend indicator (1/2 of a bloc versus 1/9) **[code]**. If G1 fails twice, the Terminal should stay an analysis tool, and that is a legitimate outcome. A read-only screener that ranks liquid coins by relative strength and helps avoid deep drawdowns is roughly what the published evidence supports. It needs no execution layer to be useful.

## Conclusion

The Terminal is missing many features, but they are not equally urgent. Measurement is missing, and every other gap depends on it. Derivatives columns, Telegram alerts and Claude order proposals all look like progress, but without a ledger each one only adds more unvalidated output. The code already contains the right instinct: the gateway refuses order endpoints until a ledger proves an edge net of costs. The roadmap simply builds the instrument that can answer that question. It also reorders the obvious wish list. The most evidence-backed data additions come from candles already downloaded. The data that must start first is the data that cannot be backfilled, 30-day-capped positioning series, because every unrecorded month is lost for good. Claude's first useful role needs no network exception at all.

One architectural decision unlocks most of the roadmap: a headless Node worker that reuses the TypeScript engine. It turns a browser-bound scanner into something that can record a ledger around the clock, send background alerts, replay history through identical code, and later host execution behind a deterministic risk gate. It also forces an overdue amendment, because ADR-0003 and R8 police the browser's CSP but not what a Node process contacts. Writing that egress list down keeps the "no network at runtime" principle meaningful as the Terminal grows from a screener toward a trading system.
