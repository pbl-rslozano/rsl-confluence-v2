# KIT-003 — SemVer version and build stamp (kit 1.2.0)

**Kit:** rsL Core Kit 1.1.0 (shown until now as `v1.1 2026`) → **1.2.0** · **Decided:** 16 Nov 2026 by rsLozano (owner) · **Severity:** medium (display format, every app)

## Problem
Apps showed their version as a number plus a year, for example `v1.0 2026 · build 20261116`. `buildStamp()` took a `year`
argument and glued it on, so the string was not a version that tools understand (it is not SemVer, it carries a year that
only repeats the build date, and the leading "v" and the dot separator differ from the identity skill's footer form
`Powered by rsL AppName · 1.0.0 · build 20261116`). The kit itself used the same shape (`v1.1 2026`), and the kit's own
`package.json` version `1.1.2026` was not a valid SemVer number.

## Decision
The owner decided on 16 Nov 2026 that the version and build metadata format changes everywhere to SemVer plus the build date:
`1.0.0 (build 20261116)`. There is no leading "v" and no year. Legacy conversion: `v1.0 2026` becomes `1.0.0`, `v1.1 2026`
becomes `1.1.0`. A CI build may later extend it to `2.8.0 (build 1482 · a1b2c3d · 2026-11-16)`; that is not part of this change.

## Change (1.2.0)
- `core/rsl-brand.js`: new exported `semver(version)` pads a numeric version to `MAJOR.MINOR.PATCH` (`1.0` → `1.0.0`, `2` → `2.0.0`,
  `2.7.0` stays); a non-numeric version (`next`, `2.8.0-rc.1`) is shown as given.
  `buildStamp({ version, year, build })` returns `${version} (build ${build})`; `year` is still accepted, and ignored.
  The version is trimmed; a blank or missing version (`""`, spaces, `undefined`, `null`) gives `build 20261116` and `Powered by rsL Name · build 20261116`,
  a blank build gives the version alone, and both blank give `""` / `Powered by rsL Name` (review fix: never "undefined", "null" or a stray space).
  `poweredBy(app)` returns `Powered by rsL ${name} · ${version} · build ${build}`. The brand block `title` reads `${name} ${stamp}`.
  JSDoc examples updated.
- Kit file headers, `README.md` (title, versioning section, footer), `package.json` (version `1.2.0`, description) and
  `tokens/rsl.tokens.json` (`$description`) show `1.2.0`.
- `tests/core.test.mjs`: the stamp and footer strings updated; new test for the normalisation cases and the brand block.
- `KIT-MANIFEST.sha256` regenerated (release check R4): same 18 files, new hashes for the files above.
- App side (not kit files): `rsl/app-info.ts` `coreKit` is `"rsL Core Kit 1.2.0"`; the types file declares `semver`; the backup file
  `appVersion` field is the stamp (`2.7.0 (build 20261111)`); the Coffee Kit display string is `1.1.0`, derived from the kit data's
  `kitVersion` (the Coffee Kit data, images and hashes are untouched); release check R19 checks the user guide against
  `<version> · build <build>`; the SBOM component version is the full package version.

## Guard
- `packages/core/tests/core.test.mjs` pins the stamp, the footer, the brand block title, the normalisation cases and the blank / missing version and build cases.
- `apps/confluence/web/src/rsl/coffee-kit.test.mjs` pins the Coffee Kit display string.
- `tools/semver-stamp.test.mjs` scans the live sources, tests, checks, workflows, README and user guide for the old forms
  (`v1.0 2026`, `2026 · build`, `v${version} ${year}`) and checks that the app's `coreKit` follows the kit version.
- `tools/docs-parity.test.mjs` (R19) rejects a user guide still in the old format.
- Release check **R4** fails if any kit file differs from `KIT-MANIFEST.sha256`; the manifest was regenerated for this change.
- Acceptance check ID-8.2 (stamp identical in the app bar and the footer) and DS-1 / DS-2 (layout at rest) run on the built app.

## Not covered
Historical records keep the old format: CHANGELOG entries of past releases, ADRs, dated reviews, research notes, plans and specs,
KIT-001 and KIT-002, acceptance evidence, and the Arabic user guide (approved text; stale since v2.3). Builds already published
still show the old stamp.
